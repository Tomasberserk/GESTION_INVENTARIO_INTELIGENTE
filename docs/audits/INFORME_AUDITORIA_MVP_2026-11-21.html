Resumen ejecutivo

Lo sólido

  • La estructura SDD está completa: gobernanza, contexto, dominio, API, módulos, UX, calidad y operaciones tienen artefactos concretos.
  • Se documentan seis contextos de negocio, fachadas, ADRs, matriz HU/NFR → pruebas, OpenAPI 3.1 y una secuencia Alembic hasta la migración 013.
  • Se recolectaron 94 pruebas sin error de colección; las 4 unitarias y las 4 pruebas de FSM de voz pasaron localmente.
  • .env no está versionado; el repositorio solo rastrea .env.example.

Lo que impide aprobar hoy

  • La regla crítica de no FKs entre módulos se contradice con FKs activas hacia empresas, propiedad de auth_tenancy.
  • El tráfico HTTP sigue entrando por app/routers y app/services heredados; las fachadas modulares no son el camino de ejecución dominante.
  • La política de cobertura 80%/90% existe en documentos, pero no existe ni en el workflow real ni en el entorno local.
  • La E2E queda bloqueada antes de la primera petición por un entorno virtual copiado desde otra ruta y un bloqueo de TestClient en Windows/Python 3.13.

Hallazgos priorizados

DAT-03 · Crítico · Llaves foráneas cruzan límites de módulo

La documentación afirma que ninguna FOREIGN KEY cruza módulos (02-domain/module-boundaries.md:26-35). Sin embargo, app/models.py:167,212,279,348 impone empresa_id → empresas.id en tablas de inventario, ventas, soporte y agente. Como empresas pertenece a auth_tenancy, son cruces de propiedad. La migración 013 resolvió tres referencias, pero dejó esta familia de FKs. Corrección: decidir y documentar una excepción explícita de tenancy o reemplazar esas FKs por UUID indexados y validación vía fachada; después, añadir migración, prueba y ADR si cambia la decisión.

ARC-03 / ARC-08 · Crítico · El camino de ejecución conserva la arquitectura heredada

La estructura prometida exige API de módulo y lógica interna (05-architecture/module-structure.md:8-31,43-48). Pero app/main.py:16,79-81 registra los routers heredados y estos importan servicios heredados, por ejemplo app/routers/ventas.py:12, auth.py:14 y productos.py:19. Incluso app/pos_ventas/internal/service.py:8 delega en app.services.venta_service. Las fachadas existen, pero todavía no son el borde operativo principal. Corrección: migrar cada router a una fachada por módulo y retirar el acceso directo a app/services de forma incremental.

QLT-02 / DEV-01 · Mayor · La cobertura declarada no es una compuerta real

NFR-07 exige 80% global y 90% para pos_ventas (04-requirements/non-functional.md:20) y la estrategia lo repite (11-quality/testing-strategy.md:15-18). El workflow real ejecuta solo pytest tests/ -q (.github/workflows/ci.yml:36-42) y no produce cobertura ni aplica umbral. Corrección: declarar pytest-cov, ejecutar cobertura en CI, separar el informe por paquete y fallar por debajo de los dos umbrales.

ARC-05 / ARC-06 · Mayor · Import-linter no se puede ejecutar localmente y no protege todos los módulos

La configuración contiene contratos para cinco módulos y platform (.importlinter:7-87), pero no hay contrato que prohíba importar reportes_analytics.internal. En el entorno auditado no está instalado el paquete. Corrección: reconstruir el entorno desde requirements.txt, agregar el contrato faltante, y guardar evidencia de una violación deliberada fallando antes de la revisión.

DEV-01 / DEV-03 · Mayor · El pipeline real no coincide con el documento

10-devops/ci-cd.md promete lint → boundary-check → test → package → deploy, pero el YAML termina en la simulación E2E backend y la verificación frontend; no hay pasos de paquete ni despliegue, ni triggers de tag para producción en el archivo auditado. Corrección: alinear el YAML con la matriz documentada o corregir el documento para describir el pipeline externo verificable.

OBS-02 / OBS-03 · Mayor · Observabilidad documentada, no implementada

Se declaran los tres indicadores mínimos (13-operations/observability.md:19-25), pero no hay implementación de contadores/histogramas en app/. La misma documentación afirma que Redis degradará salud ante cualquier fallo (:27-34), mientras app/main.py:149-151 solo lo exige con HEALTH_REQUIRE_REDIS=true. Corrección: instrumentar métricas o retirar la afirmación; decidir y documentar si Redis es dependencia crítica.

NFR-10 / UX-02 · Mayor · La vista móvil no alcanza aún el tamaño táctil declarado

La inspección visual de la web pública a 360 × 800 confirmó que no hay scroll horizontal en inicio, registro ni login. Sin embargo, el enlace superior “Crear cuenta” tiene 44 px de alto y los campos de formulario 45 px; NFR-10 exige objetivos táctiles de al menos 48 × 48 px. Corrección: fijar una altura mínima de 48 px para enlaces CTA, inputs y botones interactivos y añadir una prueba visual automatizada del breakpoint de 360 px.

DOC-12 · Menor · Hay deriva documental verificable

00-sdd-guide.md:61-62 aún dice migraciones 001–012 y OpenAPI 3.0, pero existe migración 013 y la especificación declara openapi: 3.1.0. Esto no rompe el MVP, pero contradice la regla de documentación viva.

Plan de recuperación para la sustentación

Ahora — cerrar las pruebas demostrables

  1. Eliminar y recrear .venv desde este checkout con la versión de Python acordada; no reutilizar la copia cuyo pyvenv.cfg apunta a otro proyecto.
  2. Agregar dependencias de desarrollo faltantes y congelar versiones compatibles.
  3. Ejecutar y guardar: pytest tests -q, pytest --cov=app --cov-fail-under=80, lint-imports, npm run test:voice y npm run build.
  4. Con un PostgreSQL de prueba, correr la E2E de tendero: registrar tienda → crear producto → vender → verificar stock/dashboard → soporte → logout.

Siguiente sprint — hacer real el monolito modular

  1. Resolver las FKs de tenancy con una decisión explícita, migración reversible, ADR y pruebas.
  2. Mover cada router hacia la fachada de su bounded context; convertir app/services en código de transición o eliminarlo por módulo.
  3. Completar reportes_analytics en import-linter y probar una infracción deliberada.
  4. Modificar CI para que cobertura, límites, package y deployment estén en el orden documentado y sean bloqueantes.

Antes de presentar al profesor

  • Actualizar 00-sdd-guide.md, 07-api/README.md y cualquier cifra de “tests passing” únicamente con resultados recién ejecutados.
  • Adjuntar los XML/HTML de cobertura y el log de CI exitoso; no usar porcentajes declarativos sin artefacto.
  • Grabar una demostración breve del recorrido tendero y enlazarla a TC/HU correspondientes.
  • Hacer una demo deliberada: importar un internal/ desde otro módulo, demostrar que CI falla, revertir y mostrar que pasa.
